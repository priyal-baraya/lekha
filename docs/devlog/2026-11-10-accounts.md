# Accounts, shared shops and roles

*2026-11-10 · Phase 9: Sign-in, shops and staff*

## The request

Let different people sign in, set up their own shop, add books and see their own insights.

## The choices

- **Sign-in:** a Lekha username and password, or Google.
- **Shops:** shared, with an owner who invites staff using a one-time code. One person can be in several shops and switch between them.
- **Staff:** day-to-day work only: sell, cancel sales, add books, see stock and Insights without profit. Owners do everything else.

## What I learned

**Keep tenants apart by design, not by discipline.** Putting a `shop_id` on every table would have meant every query, forever, had to remember to filter by it. Giving each shop its own SQLite file means there is nothing to remember, and none of the tested SQL had to change.

**A web app serves everyone from one process.** A normal global variable for "the current shop" would be shared by every visitor. A `ContextVar` belongs to one page run, and a two-thread test proves it.

**Never store what you only need to check.** Passwords are stored as slow, salted scrypt hashes; invite codes as SHA-256 hashes. Neither can be read back, only checked.

**Don't reveal who has an account.** "Wrong password" and "no such user" give the same message, and take the same time.

**Hiding a button isn't security.** Every rule is enforced in the services too, and roles are read fresh on every click, so removing someone works immediately.

**Click through it like a person would.** The tests passed, but the browser check found a welcome message turning up on the wrong page, and staff being told about features they couldn't use.
