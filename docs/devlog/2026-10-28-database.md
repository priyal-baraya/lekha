# Designing Lekha's database

*2026-10-28 · Phase 2: Database and sample data*

## What I built

- `sql/schema.sql`: three tables (books, sales, sale_items) with every rule written into the database itself.
- `database.py`: one function that every part of the app uses to connect, with foreign keys switched on.
- `data/sample_data.sql`: 12 fictional books and 15 fictional sales, designed so every interesting situation appears at least once.
- 44 automated tests: most try to break a rule and check the database refuses, and the rest compare query results with hand calculations.
- `sql/01_first_queries.sql` and `query.py`: nine practice queries from `SELECT` to `LEFT JOIN`, runnable in one command.

## What I learned

**Design the tables before the screens.** Every later feature reads or writes these three tables. A mistake here gets copied into every page.

**Let the database guard itself.** Rules like "quantity must be positive" live in the schema, not just in Python. Even if the app has a bug, the database refuses bad data.

**SQLite's surprises:**
- Foreign keys are **off** by default. I proved it: without `PRAGMA foreign_keys = ON`, a sale for a book that doesn't exist was accepted.
- Without `STRICT`, SQLite will store the text "twelve" in a number column.
- A `CHECK` whose result is NULL *passes*. My date check uses `IS` instead of `=` for exactly this reason.

**Money in paise.** Storing ₹349.00 as 34900 avoids the rounding errors decimals cause.

**Record what actually happened.** Each sale line stores the price the customer paid, so changing a book's price later doesn't rewrite history.

**LEFT JOIN vs JOIN.** To find books that never sold, a normal JOIN is useless: it drops exactly the books I'm looking for. LEFT JOIN keeps them. Where the condition goes (`ON` vs `WHERE`) changes the answer.

## Testing that tests work

All 44 tests passed on the first run, which is suspicious. So I checked that at least one could actually fail, by switching off foreign keys and watching the bad data get in.
