# Security hardening

*2026-11-10 · Checking every way in*

## The request

Add all the security checks Lekha needs.

## How I approached it

I went through every way in: signing in, staying signed in, what each role can do, text that ends up on screen, the outside service (Open Library), the size of inputs, the server's settings, and the packages Lekha depends on. Then I ran two scanners: **pip-audit** (known vulnerabilities in packages) and **bandit** (risky code patterns).

## What I found

- Book titles, names and reasons were shown as **Markdown**. A title with `$` turned into maths; a name could fake bold text or load a picture from another website.
- The **change-password form didn't count wrong guesses**, so it bypassed the lockout.
- **No limits** on password length, guesses spread across accounts, sign-ups, or invite-code guesses.
- **Changing a password didn't sign out** other tabs, and a till left open stayed signed in forever.
- Streamlit listened on **every network** by default, without HTTPS.
- Open Library's answers were **trusted as they came**.

The packages had no known vulnerabilities, and every SQL query the scanner flagged turned out to be safe.

## What I learned

**Escape for where the text goes.** HTML escaping wasn't enough, because Streamlit renders Markdown, with its own extras. The browser check found one more: bare web addresses became links even after escaping.

**A scanner's warning is a question, not a verdict.** Bandit flagged seven SQL strings. Reading each one showed they were safe. Marking each line with its reason, rather than switching the check off, means a new risky query will still be caught.

**Write down what isn't covered.** HTTPS, two-step sign-in and encrypted files depend on how Lekha gets hosted. `docs/security.md` lists them, so nobody assumes they're there.
